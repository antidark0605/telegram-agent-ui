# 分階段整合計畫

Revision: 2 — 2026-10-16

目前 0.2.0 包含可設定身份／Usage、任務進度及服務通知純顯示核心。此計畫不是部署授權，也不代表任何應用已完成接入。

## 第一階段：固定顯示契約

- 以既有任務進度操作習慣為基準，保留目前／已執行／最近活動與中斷按鈕。
- Usage四列用獨立引用段落，保留正文前後留白。
- 擴充合成測試覆蓋語言、長文、空資料、終態及不同模型名稱，不連真實Bot。
- 討論格式錯誤分類與傳輸退回的共用契約；未完成前不把既有應用的重送邏輯搬入核心。

## 第二階段：單一應用先接入

- 消費應用引用固定完整commit或已驗wheel，不在啟動時抓main。
- wheel 同時含 profiles 與 service_lifecycle；後者維持 submodule import。模型、帳號與 fast 資料仍由應用核實後提供。
- 在應用內把其已核實資料轉成UsageView／ReplyView；保留原模型來源、Agent呼叫及會話。
- 由既有傳輸層發送或編輯render結果，不新增第二個訊息接收程序。
- 自驗授權／topic／task／message綁定；取消只停止本任務；完成移除按鈕。
- 真實客戶端確認上下留白與Usage四項分段。未驗證的能力明確標NOT VERIFIED。
- 保留升級前套件版本與可回復步驟，不改其他應用或服務。
- renderer/profile 選擇須隨 accepted task 保存；有投遞收據的舊任務保留原 renderer，避免升降版改變重播文字與分段。raw 仍會顯示 Markdown 跳脫字元；Rich/classic 的排版要另驗，不拿 UI 純文字分段替換既有 Markdown 傳輸。
- 服務通知只在 ready 後送給已授權且實際使用過的 chat/topic，同一服務 instance 不按 agent 重複通知；原因需外部證據。詳細責任見 [通知契約](service-lifecycle.md)。

## 第三階段：其餘應用接入

共用同一公開核心，平台啟動、程序管理、來源資料、Worker／Job狀態及附件安全留各應用。不同顯示欄位透過明確介面擴充；不要在核心加入依專案名稱分支。

## 後續候選範圍

模型清單項目格式、按鈕排列、明確格式拒絕分類、附件呈現可另提設計。模型選擇下一次任務與真正載入／切換服務是不同操作：只能共用選單資料，不共用未核實的執行流程。

傳輸重試、持久化與收據具有送達語義；不因顯示相似就合併。不確定是否送達時不要無條件改格式重送，也不要為了送成功自動移除topic。

## 接入通過條件

- 固定套件來源可重現安裝，建置／測試通過。
- 任務身份、時間、按鈕與終態正確；外人／錯topic／舊message／過期task均無法誤中斷。
- 不修改模型正文、附件標記與實際投遞對象。
- Usage未知明示；行分隔在實際Telegram客戶端確認。
- 沒有私人資訊被放入公開核心或測試。
